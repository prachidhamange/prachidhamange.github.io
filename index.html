Microsoft · Outlook · Compliance

Report A Concern - Digital Services Act

I designed the backend that removes reported content from Outlook under the EU Digital Services Act, and drove the design to sign-off with principal engineers and engineering managers.

Context

The Digital Services Act puts legal obligations on how platforms act on reported content. In Outlook, when a user reports a mail, that mail has to be deleted from every recipient's mailbox, correctly, auditably and within the regulatory deadline.

What made it hard

Volume was modest, hundreds of reports a week. The difficulty sat inside each report: one mail can have hundreds of recipients, every delete has to happen, and the outcome of each one has to be recorded for audit. The service also needs access to mailboxes it doesn't own, and that access had to be tightly controlled.

What I did

  • Worked with legal, compliance and product to turn the legal requirements into technical contracts.
  • Designed the mass-deletion flow as event-driven: reporting a mail raises an event that asynchronously fans the delete out to every impacted mailbox.
  • Aggregated the per-mailbox responses into a single result, so every report has a complete record for compliance and audit.
  • Made the per-mailbox handlers idempotent and isolated failures per mailbox, so one failure is retried without repeating or blocking the rest.
  • Built parallel gRPC and REST execution paths, and authored and evolved the protobuf contracts between services.
  • Designed the security pattern for the system's access to user accounts, choosing the token types, scopes and permissions that guard against misuse, and drove the reviews with Microsoft security experts.
  • Built the monitoring and observability that detect failures and downtime in the flow.
  • Drove the design discussions with principal engineers and engineering managers to a final design.

Result

More than 99.9% reliability against regulatory deadlines, with no report silently dropped.

Microsoft · Outlook Web · Security and rollout

Outlook Platform migration: .NET Framework to .NET Core

I drove Outlook Web's part of a high-priority, Microsoft-wide security initiative: moving its services onto OS-managed virtual-account identity, rolled out ring by ring across about 0.5M machines.

Context

Outlook Web's backend authenticated with a legacy credential model that had built up as security debt across a live fleet. A virtual account is managed by the operating system, so there is no service password to store, rotate or leak. The identity change ran inside the service's larger migration from .NET Framework to .NET Core.

What made it hard

We were carving a path with three versions of the same service in production at once. Any of them could be serving traffic on a given machine, and the newest had to be introduced without breaking the other two.

VersionRuntimeIdentityRole during the rollout
Legacy.NET FrameworkLocalSystemStable; served traffic whenever .NET Core was turned off
Modernised.NET CoreLocalSystemStill stabilising
Modernised and secured.NET CoreVirtual accountBeing rolled out ring by ring

The service could not be paused while it moved. Each environment surfaced auth, permissions and secrets-management failures that only appeared once the new identity was in place, and fixing some of them needed agreement from auth and security teams in other orgs.

What I did

  • Laid the path for the rollout: identified the dependent APIs and services, and made sure the right configuration was in place before any ring started.
  • Chose an incremental migration over a big-bang cutover, so a problem would stay inside one ring, and designed the rollout across 5 environments with telemetry gates and rollback at every ring.
  • Root-caused the failures each ring exposed before promoting the next.
  • Used AI agents and tools to build the monitoring dashboards, automate the rollout checklist steps, and send status updates to PMs, dependent teams and leadership.
  • Gave on-call engineers knowledge-transfer sessions and runbooks so they could handle incidents related to the migration.

Result

Outlook Web's services moved to virtual-account identity one ring at a time, with each expansion gated on checks and telemetry. The incident described under on-call happened during this rollout, and its fix made the rollback path safe.

Microsoft · Outlook · Enterprise security

Outlook cloud signatures for enterprise admins

When the move to cloud signatures broke enterprise admins' ability to manage their users' signatures, I took a ~500-tickets-a-week escalation through a two-phase plan to a secure, reviewed design that restored admin access. Related escalations fell by about 99%.

Context

Outlook moved signatures from local storage to the cloud. Because the storage location changed, admins lost the access they relied on to create, read, update and delete signatures for users in their tenants. Tenants filed around 500 tickets a week asking for a fix, or to be moved back to legacy signatures where the experience still worked.

What made it hard

Nobody had a full picture of what had broken, or whether there were gaps no one had reported yet. Infrastructure limits made it hard to exclude affected tenants from the feature flight. The real fix meant an admin acting on another user's data, which needed agreement from security experts, Outlook data store owners and privacy reviewers.

What I did

Phase 1: relieve the impact. I built a self-serve command admins could run to opt out of cloud signatures. It took the burden off on-call engineers and worked around the infrastructure limits on excluding tenants from the feature flight.

Phase 2: understand the full problem. I worked with PMs to gather feedback from affected admins and tested cloud signatures myself. This found gaps that hadn't been reported, and gave a clearer picture of what users expected and why the feature had been built the way it was.

The design: restore admin access safely. I drove the end-to-end design to let admins manage users' signatures again, and engineered its security pattern. I backed each proposal with data and took it through security experts, data store owners and privacy reviewers.

  • Defined the scopes and permissions the caller's token must carry, so the blast radius of any one token stays contained.
  • Added role-based access control so only authorised admins can create, read, update or delete their users' signatures.
  • Built the cloud configuration APIs admins use to manage signatures across their organisation.

Result

Admins manage signatures across their organisation themselves, through access limited to signatures and to authorised roles. Related escalations fell by about 99%, and the design laid the foundation for similar third-party access to user-level settings in a secure, compliant way.

An incident I owned

Severity 2: Outlook Web availability drops to zero after a rollback

What happened. During a bake period in the virtual-account rollout, a separate production incident forced us to turn off the .NET Core version of Outlook's platform services so the older .NET Framework version could serve traffic. Once that incident was resolved, .NET Core was turned back on.

Impact. Machines that carried the virtual-account configuration started returning 403 errors, and availability of Outlook Web services on those machines dropped to zero. It was raised as a severity 2 incident.

Investigation. 403 errors pointed at service authentication. The .NET Core version could run with or without the virtual-account configuration, and the errors came only from machines that had it, so I focused on what that configuration changes. Machine logs on every affected server showed the same http.sys error: insufficient permissions for the outlook.com URL.

Root cause. The virtual-account configuration makes two OS-level changes. It runs the service under a new identity, and it reserves the service's URLs exclusively for that identity so it can listen for live requests. When .NET Core has to be turned off, existing logic cleans up that URL reservation so the .NET Framework version, running as LocalSystem, can serve the traffic. Re-enabling .NET Core brought back the virtual-account identity but not the reservation, so the service no longer had permission to listen on its own URL.

Fix. I fast-tracked a change so that the rollback cleanup also removes the virtual-account identity configuration. A .NET Core service re-enabled after a rollback now runs as LocalSystem, like the older version, and can serve from the URL without an exclusive reservation.

Follow-up. I updated the playbook and the shift handoff notes to call out this failure mode, with a clear instruction: if .NET Core is rolled back for any reason, do not re-enable it on machines with the virtual-account configuration.

Microsoft · Engineering productivity

AI agents for incidents, rollouts and large codebases

I built AI agents and workflows that take routine work off engineers, and they were adopted across the org.

Incident investigation

Many incidents follow the same investigation pattern. I automated these steps and taught them to an agent:

  1. View the dashboards for the affected APIs.
  2. Isolate the affected regions.
  3. Pull logs from those regions.
  4. Look for recent flight changes or code merges.

Incidents that follow the pattern no longer queue up for on-call engineers, who can spend their time on the rare incidents that don't.

Rollout safety

I used Copilot and Claude Code to build monitoring dashboards and a checklist check that runs before each rollout. Together they give a clear picture of the service's current state, and of whether it is safe to expand the modernised versions further.

Understanding large codebases

The biggest gain was in understanding large codebases quickly. Using AI, we found significant encryption-related gaps in a short time. That let us prioritise the feature correctly, set the right expectations on its timeline, and deliver it to the client. The workflows are also part of how the team reviews pull requests.
